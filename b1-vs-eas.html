Decision Memo · No. 2 — Delivery Backbone Remote-Module Framework · Expo Host · 2026

B1 Pragmatic LoaderversusEAS-Native Delivery

Same runtime, different backbone. Both proposals run plain-JS modules in the shared Hermes runtime behind a scoped SDK, error boundaries, and a kill-switch. They differ only in the delivery backbone — who stores, signs, gates, and ships the bytes — and in who you become: a loader author, or a fork maintainer.

This is not Memo No. 1 (EAS vs Re.Pack) again — that settled which existing machinery to bend. This memo asks: bend it at all, or build a 500-line backbone you fully own?

The one-sentence answer

Start on B1's thin custom backbone to ship the first module in ~3 weeks with zero forks to maintain — and keep the EAS sidecar as the engineered transport swap for when rollout, caching, and cadence pressure actually arrive.

Pick B1 when…

  • One owner + AI agents; first module must ship in weeks, not a quarter
  • You refuse to track a fork of expo-updates through every Expo SDK release
  • Per-channel targeting is enough for v1 — no staged % rollout yet
  • You want every part boring & replaceable: R2, Actions, ed25519, esbuild

Pick EAS when…

  • Staged --rollout-percentage, republish-rollback & a dashboard must exist on day one
  • You'd rather adapt battle-tested download/cache/signing than hand-roll it
  • Mechanical runtimeVersion gating beats trusting your own semver check
  • Two engineers and 8–12 weeks are acceptable for production-grade delivery
02

Same Runtime, Different Backbone

spine identical · branches differ

The runtime spine below — fetch → verify → evaluate → mount → error boundary — is drawn once because both proposals implement it identically: plain-JS bundle, host singletons via externals, scoped SDK at register(), circuit breaker, remote kill flag. Everything that differs lives in the two colored branches that feed it.

B1 — custom, ~900 LOC you write EAS — adapted, fork you maintain Shared — identical contract in both

Because the spine is shared, the module contract — manifest, capabilities, mounts, register(scopedSdk), signed artifact — is the durable interface. The backbone is a transport. That single fact powers both the repo answer (§03) and the swap path (§06).

03

The Repo Question

the stated hesitation · answered head-on
"I am hesitant of using a new GitHub repo for each module." — Owner, stated constraint for this memo
WHAT THE SPEC ACTUALLY REQUIRES (D5 / S1–S2): agents work in an isolated workspace — "its own repository or an isolated package with mechanically enforced boundaries" — and have no write access to the host/core repo. Repo-per-module was one mechanical realization B1's draft happened to sketch, not a requirement. Any topology that keeps agents out of the host repo and routes publishes through the pipeline satisfies the spec.

Four realistic topologies, graded. Containment grade = how well it enforces "agent cannot touch host / cannot self-publish". Ergonomics grade = what it feels like to operate solo at 10–50 modules.

Conclusion: hesitation justified — one monorepo, bot-mediated publish

The repo-per-module hesitation is correct: it buys containment the spec never asked for (the requirement is no write access to the host repo — D5/S2) and pays for it in sprawl, N CI configs, and discovery pain at exactly the cadence you're designing for. Both approaches work fine with one modules monorepo:

  • Layout: modules/<id>/ one directory per module · registry/channels/*.json (B1 only) · template as a directory generator, not a repo template.
  • Containment: agents work in worktrees/branches with no merge rights; branch protection + CODEOWNERS + required CI path checks ("this PR touches only modules/pets/"); only the pipeline bot merges and only CI holds publish credentials. GitHub can't scope writes per directory — so enforcement is PR review + checks + bot-merge, which is acceptable: the agent never had host-repo access in any topology.
  • B1 loses nothing material by folding the registry repo into the monorepo: promotion PRs still work as directory-scoped PRs against registry/; one-click promote is still "click Merge"; git audit log and rollback history survive unchanged.
  • EAS loses nothing either: EAS branches are publish targets, not source branches — eas update --branch module/pets/staging runs from modules/pets/ in the same monorepo.

05

Deal-Breakers, Both Ways

what could make you regret each choice

If you pick B1, accept…

Structural

Hand-rolled everything

Downloader, file cache, circuit breaker, manifest sync — each is small, but every byte of delivery reliability is yours to debug. expo-updates has already shipped these to millions of devices; you're re-deriving them at miniature scale.

Spike-gated

Hermes new Function risk

The whole plan rests on a day-1 device spike: evaluating an esbuild bundle via new Function in Hermes. Fallback (Metro module-ID offset multi-bundle) exists but costs most of a week and dents the "boring parts" story.

Known gap

Unsigned manifest in MVP

Artifacts are ed25519-signed; the channel manifest is TLS-only. A CDN-level attacker can't inject code but can flip kill flags or hide modules. Manifest signing is the first Phase-2 retrofit — a known IOU, not a surprise.

Retrofit list

Scale features are IOUs

Percentage rollout (Worker in front of R2), key rotation, runner fleet for smoke tests — all named, none built. The self-hosted Mac runner is a single point of failure and the first thing to crack at modules/day.

If you pick EAS, accept…

Permanent tax

Sidecar fork tracks upstream forever

The expo-module-host fork of expo-updates internals (FileDownloader, CodeSigning, SQLite, SelectionPolicy) must be re-synced on every Expo SDK release. Kept additive it's adaptation, not invention — but it never goes away, and you are its only maintainer.

Envelope risk

N modules ≠ 1 update

expo-updates is designed, tested, and operated for one update per app. Running N concurrent module updates through its machinery is outside the tested envelope — edge cases in the DB, selection policy, and recovery paths are yours to find first.

Vendor

EAS coupling

Pricing, ToS, rollout tooling, dashboard — all EAS. The open protocol + reference server is a real exit hatch, but exercising it means standing up the very infrastructure B1 starts with.

Convention abuse

Branches-as-registry is a bend, not a fit

module/<id>/<channel> branches as a module registry is clever and unsupported. Nothing in EAS promises this pattern keeps working as their product evolves; the Metro externals hack (resolveRequest shim) is similarly unofficial.

06

The Hybrid Truth: Transport Is Swappable

contract stable · backbone replaceable

The module contract — manifest (id, version, capabilities, mounts, requiredSdkVersion), the scoped-SDK register() shape, and signed artifacts — is transport-agnostic by design (spec G6/C8). Both proposals eval the same kind of bundle. So this is not a one-way door: start B1, swap the transport to EAS later (or the reverse) without touching a single module's source.

B1 → EAS: what the swap actually costs

  • Build/adopt the sidecar fork — the Phase-2 work you originally skipped (4–6 wks, the dominant cost)
  • Republish every module as an EAS update via CI re-run — no module source changes; manifest fields map into extra.module
  • Host release: embed root cert, dual-trust ed25519 + RSA during the migration window, map channels → branches
  • Retire ~300 of the loader's 500 lines (fetch/cache/verify); keep modctl as a wrapper over eas-cli

EAS → B1 (the exit hatch, for symmetry)

  • Stand up R2 bucket + publish Action — days, not weeks
  • Re-sign artifacts with ed25519; pin pubkey in the next host release
  • Point the loader seam at static JSON instead of loadModuleAsync
  • Drop the fork and its per-SDK-release sync ritual entirely

Asymmetry worth noticing: leaving B1 costs the fork you avoided; leaving EAS costs days of commodity setup plus a re-sign. The cheap-to-exit option is also the cheap-to-enter one — which is what makes "B1 now, EAS if earned" a low-regret sequence rather than a fence-sit.

08

Final Verdict

weighed for this owner, this quarter
Recommendation

B1 now — one modules monorepo — EAS held as the earned upgrade

Context that decides it: a single owner working with AI agents, first module wanted in weeks, and a runtime model both proposals share anyway. On those weights, B1's wins (no fork, no vendor, ~900 lines you fully own, ~3 weeks to a signed, killable, rollback-able module) land now; EAS's wins (mechanical runtimeVersion gating, battle-tested SQLite cache, free staged rollout) land at a cadence you haven't reached — and the fork tax that buys them starts charging on day one, every Expo SDK release, with one maintainer to pay it.

Memo No. 1 doesn't pre-decide this. Choosing EAS over Re.Pack answered "which existing machinery to bend if we bend one" — EAS won because Re.Pack abandons the Expo toolchain. This memo's question is bend vs build-thin, and "build-thin" keeps the Expo toolchain too. No contradiction in choosing B1 here.

  1. Run B1's day-1 spike first (Hermes new Function of an esbuild bundle on device). If it fails twice — spike and fallback — the calculus genuinely flips toward EAS, whose Phase 1 has no such gate.
  2. Adopt the §03 topology immediately: one modules monorepo, directory per module, registry/ inside it, agents in worktrees, bot-only merge/publish. Skip repo-per-module — the hesitation was right.
  3. Write the loader seam as if the EAS swap will happen (one loadModule(id, channel) facade). It costs nothing now and converts "reassess at scale" from a slogan into a 4–6 week, modules-untouched migration.
  4. Define the reassessment trigger up front: first scary promote that wants a 10% rollout, or sustained >1 module/day, or the hand-rolled cache producing its second production incident — whichever comes first.
