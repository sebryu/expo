EAS UpdatesversusRe.Pack + Module Federation

Two ways to ship AI-built, independently rollback-able JS modules into one Expo host app. Same containment model, same store-compliance footing — radically different relationships with the Expo toolchain.

The one-sentence answer
Default to EAS Updates — reach for Re.Pack + Module Federation only if truly independent module builds matter more to you than keeping the Expo toolchain at all.

Pick EAS Updates when…

  • You're committed to Expo: expo-router, npx expo start, EAS Build stay intact
  • Time-to-first-module matters — Phase 1 needs zero native code (3–4 weeks)
  • You'd rather operate a ~200-line Worker than a registry with Postgres + S3 + CDN
  • You want rollout, rollback, signing & CDN already built and battle-tested

Pick Re.Pack + MF when…

  • Modules must be independently built artifacts in an industry-standard container format
  • A module build must never be able to break (or require) a host build
  • You accept losing expo start, expo-router and expo-updates for Rspack + React Navigation
  • You're prepared to own a full registry and track Callstack's release cadence

Architecture, side by side

same skeleton, different ownership

Both stacks share the shape the spec demands: sandboxed module workspace → registry → device fetch/verify → shared-Hermes mount behind a capability-scoped SDK. What differs is how much of each layer you build and maintain — hatched boxes below are yours forever.

Ships today — reused infrastructure Custom — you build & maintain (hatch = approach color) Expo-toolchain departure

A1 · EAS Updates as module registry

You own: sidecar fork (adaptation, not invention) + ~200-LOC Worker + SDK bridge. Storage, CDN, signing, rollout, rollback: already shipped by EAS.

A2 · Re.Pack 5 + Module Federation v2

You own: the whole registry (API, Postgres, channels, rollout, kill-switch, signing) + SDK bridge — and a host now built outside Expo's tested path. Loader itself: shipped by Callstack.

05

Deal-breakers

read these before the flowchart
⚠ Re.Pack + MF — the cost of entry

You leave the Metro-centric Expo toolchain. Entirely.

  • npx expo start / expo run are gone — Re.Pack's dev server + direct Xcode/Gradle; dev-client UX partially lost.
  • expo-router is off the table — it depends on Metro's require.context; full rewrite onto React Navigation.
  • expo-updates dropped — your registry must own all OTA, including the host shell's.
  • Every Expo SDK upgrade carries Rspack-compat risk; each expo-* package the host exposes needs a smoke-test under a bundler Expo doesn't test against.
  • Hard dependency on Callstack's Re.Pack/MF-runtime cadence tracking React Native releases.

The comparison doc's words: choosing A2 means "leaving the Metro/Expo toolchain, which conflicts with building on Expo in the first place."

⚠ EAS Updates — the fine print

A fork to feed, a vendor to trust, an envelope to stretch.

  • The expo-module-host sidecar fork of expo-updates internals is a permanent maintenance tax, re-validated on every Expo SDK upgrade.
  • Multi-update usage (N module bundles, none of them "the" bundle) sits outside expo-updates' tested design envelope.
  • Deep EAS coupling: branches-as-registry, channels, rollout tooling — ToS/pricing/targeting drift is your problem (open-protocol self-hosting is the exit hatch).
  • Metro externals via custom resolveRequest is unofficial — Metro upgrades can break module builds (pinned by SDK, golden-file CI).
  • Per-user composition needs its own service anyway — EAS can't target cohorts.

Real costs — but they are adaptations of machinery you already run, not a parallel platform.

07

Final verdict

honest about both

The case for EAS Updates

Roughly 80% of the hard, already-debugged problems — resumable downloads, hash verification, cert-chain code signing, the cache database, rollout and rollback semantics — already exist inside expo-updates and EAS. A1 adapts them instead of rebuilding them: the only genuinely new pieces are a sidecar fork, a ~200-line Worker, and the SDK bridge every option needs anyway.

It keeps you inside the ecosystem you're explicitly building on: Metro, expo-router, npx expo start, dev-client, EAS Build all keep working, and host/module compatibility falls out of runtimeVersion for free. Its real liabilities — the fork's upkeep, EAS coupling, operating outside expo-updates' tested envelope — are maintenance risks, not architecture risks, and the open update protocol leaves a self-hosting exit.

The case for Re.Pack + MF

A2 is the architecturally cleaner answer to "independent modules": real independently-built artifacts in an industry-standard container format, total build isolation, the slickest version-skew story (host profiles + requiredVersion graceful rejection), and a loader maintained by Callstack rather than forked by you.

But the entry fee is the Expo toolchain itself: Metro replaced by Rspack, expo-router rewritten onto React Navigation, expo-updates dropped, every SDK upgrade a compatibility gamble on a path Expo doesn't test — plus a full registry (API, Postgres, CDN, signing, rollout) that you build and operate before the first module ships. For a project whose premise is building on Expo, that's paying a platform migration to buy build isolation the spec never demanded.

Bottom line

Both deliver the spec's non-negotiables — per-module rollback, kill-switch, soft-isolation containment, sandbox ≡ production for AI agents. EAS Updates gets there in weeks with far less bespoke loader and ops code, inside the toolchain you've already chosen. Re.Pack + Module Federation wins on genuinely independent builds and a standard module format — at the price of abandoning Expo's toolchain, which undercuts the reason you're on Expo at all.

If neither constraint in Q2/Q3 of the decision path is truly yours, the wider comparison's recommendation also stands: the pragmatic custom-loader MVP (B1) beats both as a starting point — but between these two, EAS Updates is the clear default.
